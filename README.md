## 三、通用原理

这一节的内容与具体游戏无关，是所有 B 站小游戏共用的部分。

### 3.1 进程与引擎

B 站的小游戏不是跑在 WebView 里，而是跑在一个独立进程中：

```
tv.danmaku.bili:web
```

该进程会按需加载小游戏引擎组件。当前实测到的 Laya 引擎路径：

```
/data/data/tv.danmaku.bili/app_mod_resource/cache/appletBasic/
    miniprogram_laya_engine_component_arm64-v8a/1-0/libMiniEngine.so
```

`libMiniEngine.so` 是一个**内嵌静态 V8 的原生引擎**，它把 V8 的 C++ 符号
（约 49556 个）全部作为动态符号导出，且**没有 strip**。这一点非常关键——
它意味着可以直接从 `.dynsym` 里查到任意 V8 API 的地址。

> 注意：B 站同时支持 Laya 和 Cocos 两种小游戏。Cocos 的试玩包会走
> `biligame*/cocos-js` 分包，运行环境不同。定位前务必先确认当前游戏用的是哪个引擎，
> 判据见下一节。

### 3.2 判断当前游戏用哪个引擎

```bash
# 进程里加载了哪个引擎组件
adb shell su -c 'grep -E "libMiniEngine|cocos|libv8" /proc/$(pidof tv.danmaku.bili:web)/maps | head'
```

- 出现 `miniprogram_laya_engine_component` / `libMiniEngine.so` → Laya
- 出现 `cocos-js` / `cocos2d-js` 分包 → Cocos

### 3.3 为什么内存扫描不可行

这是整个研究里最重要的结论，也是走过最多弯路的地方。

用内存扫描器（HuntMemory、Cheat Engine 之类）搜索数值，**第一次能搜到、
改第二次搜索就变成 0 条匹配**，或者改完立刻变回去。原因不是扫描器坏了，而是：

1. 游戏的真实数据是一个 JS 对象（如 `g.playerInfo.outDiamondNum`），存在
   **V8 的堆里**，是一个 tagged 的 Smi 或 HeapNumber。
2. 界面上显示的数值、以及各种内存里能搜到的候选，绝大多数是**过程中产生的副本**：
   - 序列化后的存档字符串
   - `String(n)` 生成的临时字符串
   - 显示层的 `text` 字段
   - JIT 编译后的常量折叠结果
3. 即使扫到真值，写回去也会被下一帧从源对象重新算出来覆盖掉。

**结论：在没有拿到源对象之前，内存扫描在这类游戏上本质不可行。** 不要在这条路上
花时间。

### 3.4 唯一可靠的路径：拿到 JS 源对象

正确做法是绕过"值"，直接拿"持有值的对象"。而 JS 对象受作用域限制：

- 如果数据挂在 `globalThis` 上 → 直接可改
- 如果数据在模块闭包里 → **从 JS 层面完全不可达**

实测的游戏绝大多数属于后者：几百 KB 的 bundle 整体包在一个内层 IIFE 里，
数据单例是那个 IIFE 作用域里的顶层 `class`。从 `globalThis`、UI 树、组件树出发
做对象图 BFS，遍历十几万节点、深度 8 也找不到——因为它根本不在可达图上。

**破局点：`v8::Script::Compile` 的入参是脚本源码文本。**

只要在编译前把源码改掉，在 IIFE 函数体闭合前插入一行把它暴露到全局，就能拿到：

```js
!function(){"use strict";  ...整个游戏...
   ;try{globalThis.__hmg=g}catch(e){}
}();
```

插入位置必须落在**函数体内**。`}();` 的 `}` 之后、`()` 之前是非法的，
`try{}();` 会直接语法错误——所以要把语句插在 `}` **之前**。

### 3.5 三个必须暴露的单例

经验上，任何一款这类游戏打通只需要三样东西：

| 暴露名 | 源码里的东西 | 用途 |
|---|---|---|
| `__hmg` | 玩家数据单例 | 改数值本身 |
| `__hma` | 配置表单例 | 反查各字段的**合法上限** |
| `__hmgg` | 平台 SDK 对象 | 接管广告、存档上传 |

其中 `__hma` 极其关键。这类游戏的配置表在运行时从服务端拉，源码里没有。
而游戏代码里大量存在**没有空值保护**的 `find().字段` 写法：

```js
// VIP 界面
a.vipCfg.find(t => t.vipLv == e).vipLv
// 兵种升级
a.roleUpgradeCfg.find(e => e.lv == t.level).fragment
// 英雄升级
a.hero_upCost.find(e => e.level == level).slice
```

一旦写的等级超出配置表范围，`find()` 返回 `undefined`，取字段直接抛异常，
界面崩溃。**所以任何"等级"类字段都必须先取表里的最大值再写，绝不能写死数字。**

### 3.6 通用工具链

```
┌──────────────────────────────────────────────┐
│ LSPosed 模块（Java）                          │
│  在 :web 进程启动时 System.load 自研 .so       │
└────────────────┬─────────────────────────────┘
                 ↓
┌──────────────────────────────────────────────┐
│ libhmshim.so（C，NDK 编译）                    │
│  · 读 /proc/self/maps 定位引擎基址              │
│  · 解析磁盘 .so 的 .dynsym 得到 V8 符号 st_value │
│  · inline hook Script::Compile                │
│  · 读源码 → 判定是否目标 bundle → 改写 → 编译      │
│  · 向各 V8 context 注入探针 JS                  │
└────────────────┬─────────────────────────────┘
                 ↓
┌──────────────────────────────────────────────┐
│ 探针 JS（游戏内运行）                           │
│  · 用 __hmg 改数据                              │
│  · 用 __hma 取上限                              │
│  · 用 Laya 显示对象画悬浮面板                     │
│  · 把结果写进 Uint8Array 供回读                   │
└────────────────┬─────────────────────────────┘
                 ↓
┌──────────────────────────────────────────────┐
│ 回读（PC 侧 Python）                            │
│  扫内存找标记字符串 → 读 4096 字节 → 解 JSON       │
└──────────────────────────────────────────────┘
```

几个设计要点：

1. **不要用 frida。** 实测在 `:web` 进程里加载 frida gadget 必崩，改成中性文件名
   也没用——冲突在 frida 运行时本身。自研的十几 KB `.so` 完全够用。

2. **不要依赖 `dlopen` 按名字查符号。** 引擎是按绝对路径加载的，按 soname 查不到。
   正确做法是读 `/proc/self/maps` 拿基址，再解析磁盘上同一份 `.so` 的 `.dynsym`。

3. **注入要落在游戏主 context。** 引擎会创建多个 V8 context（引擎初始化、
   临时脚本等各一个）。探针的 `setInterval` 若注入到临时 context，该 context
   一销毁定时器就停了，表现为"注入成功但读不到数据"。
   判据：能命中源码改写的那个 context 就是主 context，此时把它的去重记录作废、
   重新注入一次。

4. **结果回读用内存标记。** 探针把 `TAG|` + `encodeURIComponent(JSON)` 写进
   `new Uint8Array(n)` 并挂到 `globalThis`，PC 侧扫这个 TAG 的 little-endian
   int 值、定位后读 4096 字节解码。注意中文必须 `encodeURIComponent`，
   直接 `charCodeAt` 会截断。

5. **热更判重要小心。** 加载器常用"长度不同才拷贝"来判重，改动只差一两个字符时
   文件长度不变，新库不会被拷进去。改完必须手动删掉目标副本。

## 四、前置条件

| 项目 | 要求 |
|---|---|
| Root | KernelSU / SukiSU Ultra 等，能 `su -c` |
| 框架 | LSPosed 可用（用于在 `:web` 进程里加载 .so） |
| ADB | 已连接，能 `adb shell su -c` |
| NDK | 用于编译 .so（本项目实测 `android-ndk-r29`，target `aarch64-linux-android24`） |
| Python | 用于 PC 侧回读脚本 |
| B 站版本 | 不同版本引擎路径会变，以实际 `/proc/pid/maps` 为准 |

## 五、风险提示

- 所有改动只作用于**本机运行内存**，重启游戏即恢复；只有主动调用游戏的存档上传
  接口才会写进服务端。
- 部分游戏的服务端会做数值校验，异常数值可能被回滚或触发风控。
- 本文档记录的是**本地单机数值研究**过程。请自行评估账号风险。
