## 2. 改探针 JS → 生成头文件

**不要手写 C 里的转义字符串。** 探针一千多行，手写转义必然出错（少个花括号
会让 `Script::Compile` 直接返回 NULL，日志只显示 `inject N: no script`，
极难排查）。

流程：

```bash
# 1. 编辑 nativelib/inj.js
node --check nativelib/inj.js     # 先过语法

# 2. 生成 inj_gen.h（每行转成一个 C 字符串字面量）
python build_inj.py
# 输出：written nativelib/inj_gen.h 18963 bytes; js 16898

# 3. hmshim.c 里是 #include "inj_gen.h"
```

`build_inj.py` 做的事：逐行转义 `\` 和 `"`，末尾补 `\n`，拼成
`static const char INJ_JS[] = "..." "...";`。

## 3.5 注入方式（LSPosed / Zygisk 二选一）

整个链路里只有**「谁把 libhmshim.so 加载进 `:web` 进程」**这一步跟框架有关，
后面的定位引擎、hook `Script::Compile`、改源码、注入探针全是纯 native，
两种方式共用同一个 `.so`，代码完全一致。

| | LSPosed | Zygisk |
|---|---|---|
| 注入点 | `handleLoadPackage` → `System.load()` | `postAppSpecialize` → `dlopen()` |
| 时机 | App 代码开始执行后 | specialize 完成、App 代码执行前 |
| 依赖 | LSPosed（Xposed 框架） | Zygisk（KernelSU 需装 Zygisk Next） |
| 生效条件 | 重启目标进程 | 重启手机（zygote 重载） |
| 换目标 App | 改 Java 里的进程名判断 | 改 `zygisk_main.cpp` 两行常量 |

两者**可以共存**：都加载同一个绝对路径，`dlopen` 对同路径返回同一句柄，
构造器只执行一次，不会重复 hook。若只想用一种，在 LSPosed 管理器里关掉模块，
或删掉 `/data/adb/modules/hmzygisk/` 后重启即可。

### 3.5.1 Zygisk 模块

源码在 `src/zyginject/`：

```
src/zyginject/
├── zygisk.hpp          官方 API 头（ZYGISK_API_VERSION 5）
├── zygisk_main.cpp     模块主体，约 70 行
├── pack.py             打包成可安装 zip
└── hmzygisk/
    ├── module.prop
    └── zygisk/
        └── arm64-v8a.so
```

核心逻辑只有三段：

```cpp
void preAppSpecialize(zygisk::AppSpecializeArgs *args) override {
    // 拿进程名，不匹配就让 Zygisk 把模块库从该进程卸掉
    const char *n = env_->GetStringUTFChars(args->nice_name, nullptr);
    ...
    matched_ = (strcmp(name_, kTargetProc) == 0);
    if (!matched_) api_->setOption(zygisk::Option::DLCLOSE_MODULE_LIBRARY);
}

void postAppSpecialize(const zygisk::AppSpecializeArgs *) override {
    if (!matched_) return;
    dlopen(kSoPath, RTLD_NOW);        // 此时 uid 已是 App 自身，能读自己的 data/data
}

REGISTER_ZYGISK_MODULE(HmZygiskModule)
```

编译：

```bash
CXX="E:/CLI/android-ndk-r29/toolchains/llvm/prebuilt/windows-x86_64/bin/aarch64-linux-android24-clang++.cmd"
"$CXX" -O2 -shared -fPIC -fno-exceptions -fno-rtti -nostdlib++ \
       -I. -o arm64-v8a.so zygisk_main.cpp -llog -ldl
```

> `-nostdlib++` 很重要：模块会被加载进**每一个** app 进程，而 app 的
> namespace 里没有 `libc++_shared.so`。代码里不要用 STL 容器，
> 用定长 `char[]` 代替 `std::string` 即可。产物应只依赖
> `liblog / libdl / libm / libc`。

验证导出符号：

```bash
llvm-readelf --dyn-syms arm64-v8a.so | grep zygisk_module_entry
# 22: 0000000000001108  232 FUNC GLOBAL DEFAULT 12 zygisk_module_entry
```

打包与安装：

```bash
python pack.py                     # 生成 hmzygisk-v1.0.zip
adb push hmzygisk-v1.0.zip /data/local/tmp/
adb shell "su -c 'ksud module install /data/local/tmp/hmzygisk-v1.0.zip'"
```

> zip 里 `module.prop` 必须在**根目录**。打成 `hmzygisk/module.prop`
> 会因为找不到 `id=` 而安装失败。

**安装后必须重启手机**。KernelSU 的机制是先把新模块放进
`/data/adb/modules_update/<id>/`，重启时才合并到 `/data/adb/modules/<id>/`。
所以刚装完去看 `modules/hmzygisk/` 是空的、只有 `module.prop` 是正常的：

```bash
adb shell "su -c 'find /data/adb -name arm64-v8a.so | grep hmzygisk'"
# /data/adb/modules_update/hmzygisk/zygisk/arm64-v8a.so     ← 重启前
# /data/adb/modules/hmzygisk/zygisk/arm64-v8a.so            ← 重启后
```

验证是否注入成功：

```bash
adb shell "su -c 'logcat -d -b all | grep HMZyg | tail -5'"
# HMZyg: injected into tv.danmaku.bili:web (handle=0x...)
# 或
# HMZyg: dlopen /data/data/tv.danmaku.bili/files/libhmshim.so failed: ...
```

`dlopen` 失败最常见的原因是 SELinux 拒绝。此时退回 LSPosed 方案即可，
两者的后续链路完全一样，不需要改 `hmshim.c`。



```bash
CC="E:/CLI/android-ndk-r29/toolchains/llvm/prebuilt/windows-x86_64/bin/aarch64-linux-android24-clang.cmd"

cd nativelib
"$CC" -O2 -shared -fPIC -I. -o libhmshim.so hmshim.c -llog -landroid
```

产物约 36 KB。

## 5. 推到设备

加载器（LSPosed 模块）从**外部存储**取源文件，自己再拷进 `data/data`：

```
源：/storage/emulated/0/Android/data/tv.danmaku.bili/files/libhmshim.so
转发：/data/data/tv.danmaku.bili/files/libhmshim.so
再 System.load(转发路径)
```

```bash
MSYS_NO_PATHCONV=1 adb push nativelib/libhmshim.so /data/local/tmp/libhmshim_new.so

MSYS_NO_PATHCONV=1 adb shell "su -c '
  cp /data/local/tmp/libhmshim_new.so /storage/emulated/0/Android/data/tv.danmaku.bili/files/libhmshim.so;
  chmod 644 /storage/emulated/0/Android/data/tv.danmaku.bili/files/libhmshim.so;
  rm -f /data/data/tv.danmaku.bili/files/libhmshim.so;
  echo deployed'"
```

> **`rm -f` 那行不能省。** 加载器的判重逻辑是
> `!dst.isFile() || dst.length() != src.length()`。改动只差一两个字符时
> 前后大小完全相同，条件不成立，新库不会被拷进去，你会以为改动没生效。
> 直接删掉转发文件强制重拷最稳。

## 6. 重启 :web 进程

`.so` 只在进程启动时加载，必须重启 `:web`：

```bash
PID=$(adb shell pidof 'tv.danmaku.bili:web' | tr -d '\r')
echo "pid=$PID"
MSYS_NO_PATHCONV=1 adb shell "su -c 'kill -9 $PID'"
```

> **不要**在 `su -c '...'` 里写 `$(pidof ...)`。`MSYS_NO_PATHCONV` 只影响参数
> 传递，`$(...)` 仍由本地 bash 先展开，结果报 `pidof: command not found`，
> 而且后续的 `kill` 会走到 Windows 自带的 `kill` 上去。先取 PID 再传进去。

然后**手动打开游戏**（B 站 → 进入「魔法领域」）。

## 8. 回读探针结果

```bash
python readtag.py <pid> HMR9
```

内部流程：

1. 用 HuntMemory 的 MCP `hm_scan` 搜索 `HMR9` 的 little-endian int
   （`int.from_bytes(b'HMR9', 'little')`）
2. 对每个命中地址读 4096 字节（`memscan <pid> read <addr> 4096 --kpm`）
3. 按 `\x00` 截断，找 `HMR9|` 后面的部分
4. `urllib.parse.unquote` 解 `encodeURIComponent`，`json.loads`

正常输出：

```json
{
 "ts": 1793529123360,
 "gok": 1,          // 拿到 g
 "aok": 1,          // 拿到 a
 "ad": 1,           // 广告已接管
 "lb": 1,           // 找到 lab_goldNum 节点
 "vi": 1,           // 找到视图 Ye
 "dia": 888888,     // 钻石当前值
 "vip": 10,
 "maxVip": 10,
 "roleMax": 30,     // 兵种等级上限
 "heroMax": 60,     // 英雄等级上限
 "powerMax": 120,
 "power": 120,
 "god": "10.5",
 "roleLv": 30,
 "heroLv": 60,
 "t2": "888888",    // refreshUI 后界面文字
 "ui": 2,           // 面板状态：1=展开 2=折叠
 "uiDup": 0         // 本轮清理掉的重复面板数
}
```

判读：

| 现象 | 原因 |
|---|---|
| `gok: 0` + `gerr: undef` | 源码改写没生效，看日志有没有 `source patched` |
| `aok: 0` | `a` 不在 IIFE 顶层作用域，检查 patch 里的标识符名 |
| `ad: 0` + `aderr: no gg` | `gg` 没拿到，同上 |
| `lb: 0` / `vi: 0` | 游戏还没进到主界面，或不在「魔法领域」里 |
| 完全读不到（无数据） | 探针没执行，或注入到了临时 context |

## 9. 悬浮面板

进入游戏后，右下角应出现 `84×34` 的「HM」小条。

| 操作 | 效果 |
|---|---|
| 点小条 | 展开为 `300×452` 面板 |
| 拖标题栏 / 小条 | 移动位置（会记住） |
| 点标题栏右侧「—」 | 收回折叠态 |
| **全部拉满** | 写入全部字段并刷新界面 |
| **兵种满级** | `outCampInfo[].level = roleMax` |
| **英雄满级** | `outHeroList[].level = heroMax` |
| **写入存档** | 调用 `g.PlayerInfo_save()` 上传 |

面板每 2.5 秒自检：被场景切换清掉会自动重建，出现重复实例会自动清理。
